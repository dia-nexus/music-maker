# 設計の記録：決めたことと理由

最初の依頼は、別のセッションが宣伝ムービーの音楽を numpy の三角波・矩形波・サイン波で作り、ぴこぴこした電子音になった、というところから始まっている。その曲を聴き比べたわけではないが、仕組みから原因は4つに絞れる。倍音が時間で変わらない（本物の楽器は弾いた直後が明るく、だんだん丸くなる）。全部の音が同じ強さで、拍にぴったり鳴る。全楽器が同じ音域に固まる。部屋の響きが無い。音色を本物に近づけるだけでは2つ目から4つ目が残るので、この道具は作曲・鳴らし方・ミックス・確かめの全段に手当てを入れている。

## 入力を「設計図」にした

動画の音楽は、映像の秒に合わせて作る。一方で音楽の側は小節と拍で考える。設計図ではどちらで書いてもよく、内部では全部を拍（4分音符=1）に直し、秒との換算はテンポの地図（rit. を含む）が受け持つ。区切りの秒が拍の区切りに乗らないときは、近い拍にそろえて何秒ずれたかを報告する。120BPM・4/4 なら1小節2秒で、6秒・10秒の区切りはぴったり乗る。

区切りには role（つかみ・紹介・盛り上げ・山場・間・展開・終わり）と mood（自由な言葉）を書く。role は勢いの既定と旋律の音域と終止の形を決め、mood は和声進行の性格（明るい・やさしい・緊張・壮大・穏やか・遊び）を選ぶ手がかりになる。気分の言葉は `spec.MOOD_WORDS` の部分一致で拾っているだけなので、書いた言葉が拾われなければ様式の既定の気分になる。

## 作曲は規則と乱数で組む

生成モデル（MusicGen など）を使う案は採らなかった。このコンテナで動かすには重いうえ、出てくる音を「12秒ちょうどに一撃」「44秒で拍を落とす」に合わせられず、Claude が直す手がかりも残らない。規則で組めば、和声・旋律・編成のどの判断も記録に残り、報告で見つけた問題をどの段で直せばよいかが分かる。seed で乱数を固定するので、同じ設計図からは同じ曲が出る。

和声は、様式と気分のタグで手持ちの進行（`styles.PROGRESSIONS`）から選び、同じ曲の中ではなるべく違う進行を区切りごとに使う。区切りが進行より長ければ2周目で代理和音（I→I/3、IV→ii7 など）と、次の和音への副属和音を入れる。2回目以降の山場だけは同じ進行を使う。曲の顔がぶれると、何の曲だったか分からなくなるので。

旋律は、曲全体で1つの動機（1小節のリズムと音の動き）を作り、4小節の句の中で、提示→リズムを替えた応答→頭を切って模続→和音の音で伸ばして終わる、と展開する。強拍と長い音は和音の音に寄せ、弱拍は音階の音のまま経過させる。跳躍のあとは反対へ戻す。音域に収まらない小節は小節まるごとオクターブで動かす（1音ずつ動かすと動機の形が崩れたので）。

声部の進め方は、前の配置から各声 ±7 半音の候補を総当たりし、動きの合計に、平行5度・8度、声の交差、上声の間隔の開きすぎ、導音の重複に罰点を足して一番安いものを選ぶ。4声なら候補は数百通りで、一瞬で終わる。

伴奏は様式の parts に役（旋律・重ね・対旋律・伸ばし・刻み・分散和音・ベース・ドラムなど）と、入ってくる勢いの範囲を書いておき、区切りの勢いで出し入れする。build の区切りは中で勢いが上がり（ramp）、楽器が小節ごとに入ってくる。

最後に、全楽器の中身がまったく同じ小節が無いかを調べ、あればドラムの飾り・和音の配置・旋律の飾りの順に変える。そのあとで、楽器ごとに癖をつけたタイミングの揺れ（弦は少し遅れて入る、ドラムはきつめ）と強さの揺れをかけ、ローファイは8分の裏を遅らせて跳ねさせる。

## 鳴らすのは FluidSynth と General MIDI の SoundFont

MIDI を書き出し、FluidSynth で GeneralUser GS を鳴らす。GM の SoundFont は録音した楽器の音を使うので、倍音の変化や打鍵の強さによる音色の変化が最初から入っている。楽器ごとに MIDI を分けて書き出すので、そのまま stems になり、4つの CPU で並べて書き出せる（60秒の曲で 3〜5 秒）。

GeneralUser GS を選んだのは、許諾が「自作の曲への利用は商用含め制限なし、同梱・改変も可」と明快で、31MB と軽く、このコンテナから raw.githubusercontent.com 経由で取れたから。リポジトリには入れず、setup で取る。32MB の SoundFont を git に入れると、このリポジトリを clone するすべてのセッションが毎回それを落とすことになる。

SoundFont も FluidSynth も無いときは、サンプルを使わない合成音（`mm/synth.py`）で鳴らす。冒頭の4つの原因に合わせて、ピアノは倍音ごとに減衰の速さを変え、弦のずれでうなりを作る。弦は鋸歯を合奏の人数ぶんずらして重ね、胴の共鳴で濾す。ギターとハープは Karplus-Strong。金管は強く吹くほど明るくなるように暗い音と明るい音を混ぜる。合唱は母音のフォルマントで濾す。GM の音には及ばないが、矩形波の重ねよりはずっと楽器に寄る。60秒の曲で書き出しに約50秒かかる。

## ミックス

楽器ごとに、まず -20 LUFS にそろえてから、様式に書いた相対音量（level）をかける。こうしておくと、SoundFont が変わって素の音量が違っても、混ざり方が崩れない。系統ごとに低域を切り、和音楽器の 250〜400Hz を削る（中低域が重なってこもるので）。残響は、数値で作った部屋の響き（初期反射と、高域ほど早く消える残響、左右は別の雑音）を楽器ごとに畳み込む。pedalboard の Reverb より響きの密度と左右の広がりが自然になる。

全体は、120Hz 以下を真ん中に集め、軽く圧縮し、ラウドネスを -14 LUFS（配信の多くの場所がこの辺りに合わせる）に、真のピーク（4倍に引き伸ばして測る）を -1 dBTP の下に収める。ナレーションの区間は 0.25 秒かけて音楽を下げる。

## 確かめ（耳の代わり）

Claude は音を聴けないので、報告が耳の代わりになる。報告に入れたのは、Claude が見て「どこを直すか」を決められるものだけ。

区切りごとの音量・音の密度・明るさ（スペクトルの重心）・左右の広がり・鳴っている楽器を表にし、隣の区切りと比べて変化が小さすぎれば知らせる。和音は、設計した和音と、MIDI から推定した和音、書き出した音から推定した和音の3つを並べる。音から推定するときは、和音ごとに長い窓（16384点、約3Hz刻み）で平均スペクトルを取り、山だけを拾う。短い窓では低音の半音が分からず、ルートを弾かない 7th の和音も取り違えていたので、和音の頭で鳴っている最低音を根音の手がかりに足した。

帯域のバランスの目安（120Hz 以下が 15〜55%、120〜500Hz が 45% 以下、6kHz 以上が 12% 以下）は、この道具で作った数本の曲を測って決めた暫定の値で、どこかの基準から取ったものではない。例の曲は 31.7%・41.6%・2.1% だった。

機械っぽさの目安（打鍵の強さのばらつき、拍の格子からのずれ、音色の系統の数、左右の相関、最後の音のあとの響き）は、冒頭の4つの原因をそのまま数えたもの。この目安が全部通っても、旋律が良いかどうかは分からない。旋律は作曲の記録とピアノロールを読んで判断するしかない。

## 分かっている限界

- 伴奏の型は4拍子で書いてある。3/4 と 6/8 は通るが、型を小節の長さで切り詰めているだけで、6/8 らしい大きな2拍の揺れは出ない。
- 1つの様式の中で使える打楽器のキットは1つ。MIDI の10チャンネルは音色を1つしか持てないので、きっかけ用の打楽器も様式のキットに合わせている。
- 合唱は GM の Choir Aahs のまま。CC0 や CC-BY で使える合唱の音源は見つからなかった（`docs/sound-sources-research.md`）。
- 旋律の動機は1小節で、句は4小節固定。8小節の大きな句や、歌のような長い旋律は作れない。
- 気分の言葉は部分一致で拾うだけなので、細かいニュアンスは和声に届かない。区切りに `progression` を書けば確実。
